# Super-agent 独立评估：从概念、设计到落地

整理日期：2026-11-02。对象：《Super-agent 设计探索：迈向更自主的 Agent 系统》（DeepSeek Harness 团队，2026-10-31）及 `dsh-superagent-prototype`。

本文是后续探索的总纲。外部解读文章只作参考，判断都回到原文和原型代码本身。分三层看：概念是否成立 → 设计是否合理 → 落地做到哪里，最后列出要验证的问题。相关材料 `analysis.md`（阅读笔记）和 `personal-agents.md`（Personal Agent 产品调研）不在本仓库。

回放评测台的代码在分支 `bench/replay` 的 `bench/replay/`，产品修复在分支 `fix/released-inputs`，跟踪事项见本仓库的 Issues。

## 1. 概念层：Super-agent 到底提出了什么

### 1.1 核心论点

去掉"连续、高效、主动、持久"四个形容词，原文真正的主张有两条：

1. **瓶颈正在从模型能力转移到人的注意力。** 单任务的上限取决于模型，多任务的上限取决于人。原文的观察是，一个人通常只能同时跟进 3 到 5 个活跃 Session。
2. **"Session"是从 LLM API 延续下来的设计惯性。** 它应该退成系统的实现细节，不该让用户去管理。

所以 Super-agent 的本质是**换了工作单元**：从"对话"变成"事项"，也就是有生命周期、有授权、能订阅多个信息源的任务对象，Session 降为可替换的执行资源。四个特征都由这次替换推导出来：

- **连续**：事项跨渠道存在。
- **高效**：多个事项并行。
- **主动**：事项可以由环境事件创建。
- **持久**：事项不随进程结束而消失。

原型的领域模型正是这么做的：Ticket、Thread、Subscription、Mandate 是一等对象，`worker-<ticket>` Session 只是 Ticket 的执行器。这和 Issue Tracker 的思路相近，只是执行者换成了 Agent。

### 1.2 是不是真问题

| 判断 | 依据 |
|---|---|
| ✅ "人在搬上下文、切 Session"是真痛点 | 多个 Coding Agent 并行用过的人都有体会；Personal Agent 产品集中涌现（见 `personal-agents.md`） |
| ⚠️ 注意力不会消失，只会转移 | 系统省掉的是派活和搬上下文的注意力，却可能增加验收的注意力：PR 更多、消息更多。原文说人"上移到决策与验收"，但没讨论验收成本会不会成为新瓶颈 |
| ⚠️ 适用条件很强 | 软件开发天然满足三个条件：产出物可验证（PR/CI）、事件机器可读（Webhook/API）、动作可撤回（PR 不合并就不生效）。个人办公三条都弱：发出的邮件收不回、没有 CI 兜底、关联更模糊。原文的证据全部来自研发场景 |
| ⚠️ "连续实体"可能变成"虚假连续" | 底层其实是多个隔离 Session 拼起来的。Router 记不全，就会出现"表现得像记得、其实不记得"，这比明确说不知道更伤信任 |

**结论**：在"可验证产出 + 机器可读事件 + 小信任圈"这个范围内，问题真实而且迫切。出了这个范围，安全、信任和验收成本这些问题会比架构问题更早暴露。原文 §8.4 自己也承认这一点。

## 2. 设计层：每个设计决策的取舍

原文把方案归结为"计算机系统经典思想的应用"。这个说法总体成立，但每个类比都有它不覆盖的地方。

### 2.1 双层架构（原文 §2）

- **我认为真正有价值的地方不是吞吐，而是"结构约束胜过提示词约束"。** 消融实验最有说服力的结果不是 p50 快了，而是：单会话下"分不分工"完全看提示词和模型临场判断（中性提示 0/5 次委派，优先委派也只有 4/5）。双层架构用"Router 根本没有执行工具"把这个判断从模型手里拿走了。可以推广的原则：**能用结构保证的，不要交给提示词**。
- **实验没有覆盖的部分**：
  - 编码工作被替换成只耗时的工具，测的是调度，不是质量；
  - 每组只跑 5 次，消息是合成负载；
  - 单会话基线没有排队或打断策略（例如 OpenClaw 的 steer、followup、collect）；
  - Router 决策是否正确（接错、挂错、漏接）完全没测。
- **可选的其他方案**：
  - 每个 Thread 一个 Actor，不设全局 Router：吞吐最高，但没人负责跨 Thread 关联；
  - 共享黑板，多个 Worker 读写同一份状态：协作更强，但冲突更难控制。

  双层架构是两者之间的折中，代价是 Router 同时承担了全局判断和全局记忆两个职责。
- **批处理**（原文 §2.1、§7.2）：长输入、短输出的调用天然适合合批。批处理换来的是吞吐，单条消息的延迟不一定更短。上限取决于"模型在一轮里能准确处理多少条 Trigger"，而这一点没有测。

### 2.2 事件驱动（原文 §3.1、§3.2）

- **订阅快路径**：Thread 的身份直接用来源系统里的天然标识（PR 号、IM 话题），便宜又可靠。原文数据显示，去掉快路径后 Router 的读缓存 token 多了 37%，完成时间却没变。所以快路径省的是成本，提不了速度。
- **真正的难点被交给了 Router 的语义判断**：原文开头的例子是"IM 里说方案 A，PR 评论里改成方案 B"，这其实是同一个 Thread 内的事。真正难的是跨 Thread 的关联，比如一封新邮件说的是哪个已有任务。原文没有专门讨论这个问题，原型也是交给 Router 用 `orchestrator_route kind=attach` 判断。
- **两级过滤**：方向正确。但误判的代价不对称，多说一句话的损失远大于少说一句，所以语义层需要校准。原文没有给出准确率数据。

### 2.3 上下文组织（原文 §3.3）

把上下文窗口当 Cache 管理，用引用图逐跳召回（Chain of Recall），这个设计很优雅。问题在于：

- 没有量化数据，比如召回需要几跳、召回失败率是多少；
- 跨月的长期记忆被原文列为开放问题（§8.1），而"持久"恰恰依赖它。

### 2.4 提前行动 / 投机执行（原文 §3.4）

这是价值最大、风险也最大的一块。CPU 的投机执行可以无代价回滚，Agent 的不行：后台复现要算力；而"认为有价值才交付"的判断如果失准，就直接变成噪音。它真正需要的是一个价值判断的标准，以及一个数字：**投机结果有多少比例被采纳**。

### 2.5 面向人的交互（原文 §4）

- 全双工（异步 ReAct）是让主会话能随时接收新指令的必要条件。原文注明它在 DeepSeek Harness 中已实现，但没有默认开启。
- 多信道规范（IM 短、GitHub 结构化、100 词上限）属于产品经验，难以量化。需要把"注意力成本"定义成可度量的指标：每个工单的消息数、追问率、被人叫停率。

### 2.6 计算、状态与环境分离（原文 §5）

- §5.1 计算与状态分离已经是成熟做法，没有争议。
- §5.2 端侧 daemon（BYOM）既是差异化所在，也是风险集中点：一旦云端被攻破，所有连上的设备都有风险；凭据也可能进入模型上下文（§8.4）。**凭据代理（Agent 能使用凭据，但永远看不到凭据本身）是这条路线的前置条件，而不是之后再补的优化。**

### 2.7 Watchdog（原文 §6）

用 LLM 判断"任务有没有实质进展"是对的，因为 Agent 最常见的故障是活着但没在推进。但存在两个问题：谁来监控 Watchdog？它本身的误判怎么办？

一个自然的改进是把两级过滤的思路也用在 Watchdog 上：先用确定性信号（报告超时、工具调用重复、错误循环、CI 停滞）快速筛一遍，可疑的再交给 LLM 判断。

### 2.8 原文没讲、但原型补上的部分

原型在**治理**层面比原文更完整：

- **Mandate**：授权来源、强度、策略版本可追溯（`docs/002-authorization.md`）；
- **准入模式**：off / observe / auto，先观察再放开；
- **Engine 单写者 + 持久化 effects**：任何外部副作用都先落盘、再执行、可幂等；
- **宿主强制**：PR 归属（`claimPull`）、result 回复的前置条件（`replies.ts`）由代码保证。

原型在实践中的核心原则可以总结为：**LLM 负责判断，代码负责约束**。`docs/000-philosophy.md` 中"尽量少占用人的注意力"是整个原型的价值观，比原文的四个特征更接近第一性原理。

## 3. 落地层：原型做到哪里

原型是 DSH 插件，约 1.3 万行 TypeScript，单机运行，SQLite 存储，接入 GitHub 和飞书。

| 原文模块 | 原型实现 | 完成度 |
|---|---|---|
| 双层架构 | `orchestrator` 加 `worker-<ticket>`，两边能用的工具按角色分开 | ✅ |
| 批处理 | 每个 Thread 一个 Eval，期间的消息进 pending 合批；候选卡片 steer 进主 Session | ✅ |
| 过滤与路由 | `policy.gate` 加 LLM 判断；订阅扇出直通 Worker；`orchestrator_trigger_handback` 交回 | ✅（轮询，没有 Webhook） |
| 上下文与召回 | 卡片截断加续读指针；`orchestrator_read` 按 ID 读取 | 部分 |
| 提前行动 | 主动规则 + 静默接单 + 主动工单可以报告 `dropped`；默认只观察 | 部分（被刻意收紧） |
| 全双工 | 超过 5 秒的 shell 命令转后台（`src/executor/background.ts`）；steer/queue 注入 | 部分 |
| 多信道规范 | 确认一次、静默工作、结果回到来源会话、100 词上限 | ✅ |
| 计算/状态/环境分离 | 只有状态持久化；三者在同一台机器上 | ❌ |
| Watchdog | 只有 Eval 超时重排（`REQUEUES=2`）、effects 重试，以及靠 Worker 自报的 `canRetry`（`src/core/stage.ts:23`） | ❌ |
| 长期记忆、Router 分片、A2A | 没有 | ❌（原文也列为开放问题） |

**整体判断**：原型扎实地验证了**单机、研发场景下的调度与治理**，这是原文最有证据的部分。持久化（分离、Watchdog）和泛化（个人场景、跨渠道关联、安全）基本还停留在原文的论述层面。

一条 GitHub 评论从进入到 PR 合并的完整调用链，见对话记录中的"调用链"一节，后续可以单独整理。

## 4. 要验证的问题

### P0：先搭回放评测台

把录制的或合成的消息流按时间灌进 Engine。Worker 可以换成能控制耗时和结果的假实现，以单独测调度；也可以换成真模型测端到端。指标直接从 Store 和 effects 里算。下面大部分验证都依赖它。

### 概念层：值不值得做

| # | 问题 | 方法 | 指标 |
|---|---|---|---|
| C1 | 注意力有没有真的省下来 | 同一批任务分别用"人管多个 Session"和"Super-agent"完成 | 派活、搬上下文、验收各花多少人工时间；人被打断的次数 |
| C2 | 验收是否成了新瓶颈 | 真实运行中统计 | 每个工单的验收耗时、PR 一次通过率、返工率 |

### 设计层：设计是否站得住

| # | 问题 | 方法 | 指标 |
|---|---|---|---|
| D1 | 双层架构对比更强的基线 | 复现原文消融实验，换成真实任务，增加"单会话 + 排队模式"一组，次数至少 20 次 | p50/p95 完成时间、被打断次数、token 和成本，以及 **Router 决策准确率** |
| D2 | Router 在高压下是否保持准确 | 消息量阶梯加压：每分钟 1 → 40 → 100 → 200 条 | 平均批大小、每条决策的延迟、`unavailable` 比例、决策准确率随批量的变化 |
| D3 | 跨渠道关联 | 设计跨 Thread、跨来源的场景 | attach 准确率，挂错与漏挂各自的代价 |
| D4 | 过滤与投机的校准 | 在真实群里开 observe 模式运行两周，人工标注是否该接 | 精确率、召回率，以及投机结果的采纳率 |
| D5 | 召回 | 一个旧任务在跨渠道被重新提起 | 召回所需跳数、召回失败率 |
| D6 | 快路径不跑偏 | 对 PR 连续提 review、CI 失败、提超出范围的需求 | 交回率、范围漂移率、是否回复了不该回复的消息 |

### 落地层：缺的部分怎么补

| # | 问题 | 方法 | 产出 |
|---|---|---|---|
| L1 | Watchdog | 注入卡死、循环、偏离目标的 Worker，测当前多久能发现 | "确定性信号 + LLM 复核"的两级 Watchdog 原型 |
| L2 | 崩溃恢复 | 在 launch、reply、relay、prepare 各阶段 kill 进程，然后重启 | 是否有重复回复、丢消息、遗留的 worktree 或 Session |
| L3 | 延迟 | 把 GitHub 轮询换成 Webhook | 首次确认的端到端延迟能降多少 |
| L4 | 安全边界 | 非名单用户在 Issue 或评论里做提示注入；Worker 读到恶意 PR 内容 | gate 是否拦得住；Worker 以智能体身份操作的影响范围 |
| L5 | 端侧分离的最小原型 | 命令执行 daemon + 凭据代理 | 安全边界是否可行，再决定是否投入云端化 |

### 推荐顺序

1. P0 评测台；
2. D4（真实数据、零风险）和 L1/L2（直接产出 Watchdog 设计）；
3. D1/D2（验证原文核心论点）；
4. D3/D5（跨渠道与召回）；
5. C1/C2（需要真实用户，周期最长，但最根本）；
6. L3–L5。

## 5. P0 进展：回放评测台（2026-11-02）

代码在 `dsh-superagent-prototype/bench/replay/`（`scenario.ts`、`sim.ts`、`run.ts`、`README.md`），冒烟测试在 `tests/replay.spec.ts`。

- **真实部分**：核心 `Engine`（Intake、订阅扇出、Eval 批处理与超时、Mandate、Ticket、Assignment、Replies）和真实的 `settingsPolicy` gate。
- **模拟部分**：
  - Router 是单服务器，一步取走所有排队的卡片，单步耗时 `1.72 + 0.78 × 条数` 秒（按原文 §7.2 拟合）；决策取场景真值，按错误率翻转。
  - Worker 有槽位、启动耗时，后续消息在下一步才读到。
  - Source 轮询延迟可调。
- **因此它测的是调度与路由机制，不测模型判断和代码质量。**

运行方式：`node --experimental-transform-types --no-warnings bench/replay/run.ts <experiment>`。每组实验合并 10 个随机种子。

### 5.1 初步结果

场景按原文消融实验的形态生成：每轮约 20 个请求、每个请求 2 条后续消息、220 条闲聊、10 条 @ 寒暄、CI 结果；请求在 1 小时内到达，单个任务工作 10–30 分钟。默认 `maxWorkers=3`、准入模式 `off`。

| 实验 | 结果 | 含义 |
|---|---|---|
| 基线 | 200 个请求全部确认、全部完成；确认回复 2.5s；结果 p50/p95 = 105.5/189.4 分钟；Worker 槽位等待 p95 = 182 分钟；Router 繁忙率 0.9% | **瓶颈在 Worker 槽位，不在 Router** |
| Worker 数 1→8 | 结果 p50 从 330 分钟降到 38 分钟，近似反比 | 这类负载下，完成时间主要由执行容量决定 |
| Router 压测（送到 Router 的速率 1→60 条/分钟，16 个 Worker） | 平均批大小 1.00→2.37；分摊到每个决策的时间 2.50→1.51 秒；确认回复 p95 从 2.5 秒升到 20.3 秒（40 条/分钟时 11.3 秒） | 批处理按预期摊薄成本；但**这只是对拟合参数的自洽检查**，没有验证"批变大后决策是否仍然准确" |
| 轮询间隔 0/10/60/120 秒 | 确认回复 p50 为 2.5/7.7/33.1/63.7 秒 | 在 GitHub（通知轮询至少 60 秒）上，**首次响应延迟几乎全部来自轮询**，Router 推理只占零头 |
| 跨 Thread 后续消息被 @ 的比例 0/0.5/1 | 丢失比例 100%/45%/0%（丢失指没到达工单） | **在默认模式 `off` 下，跨 Thread 且没 @ 智能体的补充信息会被 gate 静默丢弃**。"连续"目前依赖人主动 @ |
| Router 错误率 0/5%/10%/20% | 漏接请求 0/13/22/36，误接 0/5/10/18，漏挂 0/10/14/36（10 轮合计） | Router 判错会连锁放大：漏接一个请求，它后续的跨 Thread 补充也挂不上 |

### 5.2 对第 4 节问题的影响

- **D2（Router 吞吐）**：在团队规模的负载下，Router 远没到瓶颈。要回答的问题从"Router 会不会被挤爆"转成"大批量下 Router 是否仍然判断正确"。这需要接真实模型。
- **D3（跨渠道连续）**：找到一个具体缺口。可以考虑的方向：
  - 在 observe 模式下给"疑似指向已有工单"的消息单独建一条候选通道；
  - 让 Router 在已有工单的上下文里低成本判断 attach。
- **L3（延迟）**：上 Webhook 的收益可以直接量化。在 60 秒轮询下，确认回复 p50 约 33 秒；改成推送约 2.5 秒。
- **容量**：在 Router 之前，Worker 并发（以及成本）更早成为瓶颈。可以把"按优先级调度 Worker 槽位"列为新的探索项。

### 5.3 真实模型当 Router（2026-11-02）

`bench/replay/llm-router.ts` 让真实模型充当主 Session。以下部分全部来自产品代码，没有重写：
- system prompt：`composePrompt`；
- 工具：`mainTools`，所以 `orchestrator_route` 的 schema、字段检查和对 Engine 的调用都是原版；
- 候选卡片：`candidateCard`；
- Worker 结果转发：`resultRelay`；
- 资源读取：`readResource`。

每次模型调用的真实耗时计入虚拟时钟，期间到达的卡片按 DSH 的 steer 方式注入同一轮。

与产品的差别有四点：
- 用固定的历史上限代替 DSH 的上下文压缩；
- 没有 DSH 自身的 system prompt 和 skills；
- 修改设置和提示词的工具、推断型评估工具都返回"不可用"；
- 不发送 follow_up 通知。

模型为 DeepSeek 官方 API 的 `deepseek-flash`。语料是中文团队群聊（`corpus.ts`），每组 3 个种子。

| 场景 | 请求被接单 | 闲聊被建工单 | 误建工单 | 跨 Thread 补充挂对 | 确认 p50/p95 | 单次调用 p50/p95 | 调用次数 | 输入 token（命中缓存） |
|---|---|---|---|---|---|---|---|---|
| 小团队 1 小时（8 个请求、40 条闲聊、8 条 @ 寒暄） | 24/24 | 0/24 | 0 | 23/23 | 2.1/2.7s | 1.6/4.3s | 225 | 5.0M（92%） |
| 突发（3 分钟内 12 个请求、12 条 @ 寒暄） | 36/36 | 0/36 | 0 | 36/36 | 1.9/5.9s | 1.4/3.2s | 308 | 7.5M（83%） |

**结论**：
- 在这套语料上，`deepseek-flash` 的路由判断和真值完全一致。
- 平均每张卡片约 2 次调用：一次 route，一次收尾说明。另外会主动用 `orchestrator_read` 查工单。
- 大约 90% 的输入 token 命中前缀缓存。这和原文"Router 每步长输入、短输出"的判断一致；成本主要取决于缓存命中率。
- 这一结果**不能**推广为"Router 判断没问题"。语料偏简单：请求意图清楚，补充消息都用"X 那个"明确指向任务。突发场景的平均批大小只有 1.03，模型单次调用约 1.5 秒，这个密度下几乎不形成批，所以 D2（大批量下的准确率）**还没有测到**。

**过程中发现的问题（真实存在，原因在产品代码）**：

- **工单结束时未读的消息会"无声回流"。**
  - 机制：工单结束时，人发来但 Worker 还没读过的消息，会由 `Tickets.letGo`（`src/core/tickets.ts:288-308`）从 `fanout` 里移除，并重新送去 Eval。但这一步不记录原因，候选卡片上也不显示。Worker 主动交回的消息则有 `handed_back` 字段说明原因，两者形成对比。
  - 实测：模型第二次看到同一条消息时，多次判定为"重复投递、已处理"，然后 ignore。人的补充需求就这样被静默丢掉。
  - 触发条件：Worker 发出 ready 报告的那一步里有新消息到达，且工单在 ready 时立即结束。纯飞书工单没有绑定 PR，会在 ready 时立即结束，所以最容易碰到；GitHub 工单要等 PR 关闭才结束，基本碰不到。
  - 改进建议：在 disposition 里记录 `released: [{ticket_id, reason: 'ended before its worker read it'}]`，在卡片上显示出来，并在 `dispatch.md` 里说明"回流的消息不是重复消息，应 attach 回原工单，或者当作新请求接单"。
- **同一 Thread 上的后续消息也有同样的竞态。** 规则 Router 已改为把回流的消息 attach 回原工单，这也是提示词期望的行为。

### 5.4 难例语料（2026-11-02）

在 `corpus.ts` 里加了难例，每条都按 `dispatch.md` 标好"哪些结果算对"。用标准答案模拟器跑一遍是 78/78，说明标注和评分自洽。

- **兄弟工单**：同一页面或功能的两个不同问题同时开着，比如登录页按钮错位和登录页验证码看不清、订单导出乱码和订单导出时间列变数字。补充消息必须读出说的是哪一张工单。
- **和任务相关的难例**：叫停、问进度、别人换种说法重复提、话题相近的新需求。
- **和任务无关的难例**：指代不明（"刚才那个也顺便处理一下"）、纯技术提问、"先别动手等我确认"、"你不用管"、委婉提出的新需求。

场景：30 分钟、8 个任务、每组 3 个种子，共 78 个难例和 30 条跨 Thread 补充。实验名 `model-hard`。

| | 请求接单 | 误建工单 | 跨 Thread 补充挂对 | 难例正确 | 单次调用 p50/p95 | 确认 p95 | 输入 token（缓存命中） | 花费 |
|---|---|---|---|---|---|---|---|---|
| oracle | 24/24 | 0 | 30/30 | 78/78 | — | 3.0 秒 | — | — |
| deepseek-flash | 24/24 | 0 | 29/30 | 77/78 | 1.4/4.0 秒 | 7.3 秒 | 10.8M（84%） | 未单独计量 |
| deepseek-v4-pro | 24/24 | 1 | 28/30 | 77/78 | 2.9/19.2 秒 | **182 秒** | 17.6M（76%） | 约 20 元 |

v4-pro 第一次运行时余额耗尽，那次中断数据不可用。上表是充值后重跑的完整结果。中断那次的部分判断（比如"先记下，下周再做"被接单）在重跑中没有复现，说明**同一模型多次运行之间的差异不小**，3 个种子只够看大方向。

**观察**

1. **两个模型在难例上准确率相当，都是 77/78。**
   - 叫停、指代不明、"先别动手"、委婉请求、话题相近的新需求，全部判对。
   - 兄弟工单之间都没有挂错一次。
   - 在这个复杂度上，路由判断不是瓶颈。
2. **差别在速度上。**
   - v4-pro 单次调用 p95 为 19 秒，最慢的单次超过 180 秒，一次慢调用会让后面排队的请求确认等到 3 分钟以上。
   - flash 确认 p95 为 7 秒。
   - Router 是串行的单点，**尾部延迟比平均准确率更关键**。按这批数据，选 flash 当 Router 是对的；大模型更适合交给 Worker。
3. **flash 的错误集中在"把 policy 用错了地方"。**
   - "订单导出也支持按时间范围筛选""验证码那个，产品说干脆换成滑块"两条被它以"新功能需要先定设计"为由忽略。
   - 但 policy 原文写明，规则只约束主动候选，显式请求按 dispatch 处理。
   - policy 和 dispatch 放在同一个提示词里会互相干扰。
4. **重复请求和规则不一致。**
   - `dispatch.md` 规定"话题相近的消息是新请求，绝不挂到已有工单"。
   - 实际上，flash 把 8/12 条重复请求挂到了已有工单，v4-pro 挂了 4/12，其余都是忽略。两者都没有按规则新建重复工单。
   - 模型实际做的比规则更合理。规则应该跟进，比如允许"挂到已有工单，或判为疑似重复后请人确认"。
5. **标注本身有局限。** "不用你弄了，bob 已经在改了"标注为"无具体所指，应忽略"。但种子 3 里，它前面正好是 carol 的验证码请求和 bob 关于验证码的补充。v4-pro 两次运行都推断为叫停验证码工单，这其实是合理的推断。随机放置的难例可能碰巧有了上下文，判错的情况需要逐条看。

### 5.5 批处理与准确率（D2）

**按速率加压（`model-saturation`）不适合测这个问题。** 名义 20 条/分钟、实际约 14 条/分钟，跑 2 个种子：
- 平均批大小只有 1.11，准确率却明显下降：跨 Thread 补充丢 6 条，误建工单 6 张。
- 原因不在批大小：
  1. 工单周期很短，结束后未读的补充被撤回、重新送审，模型认为"重复投递"就忽略了。这就是 §5.3 里的回流问题，在短周期工单上更常见。
  2. 请求数超过语料里不同任务的数量，任务文本出现重复，补充消息本身就有歧义。
- 速率越高，这两个混淆因素越强，所以没有继续跑 60 和 120 条/分钟。

**改为强制批大小（`model-batch`）。**
- 内容固定：12 个不重复的任务，工单全程开着，共 68 个难例和 23 条跨 Thread 补充，2 个种子。
- Router 要等攒够 N 张卡片才开始处理，等待上限 600 秒，这一组只看判断准确率，不看确认时延。
- 每种批大小都配一组标准答案模拟器作对照，因为排队等待本身也会丢消息。

| 批大小 | 实际平均批 | 难例正确（oracle / flash） | 跨 Thread 补充挂对（oracle / flash） | 误建工单（flash） | 模型调用 | 输入 token | 单次调用 p50/p95 |
|---|---|---|---|---|---|---|---|
| 1 | 1.0 | 68 / 68 | 23 / 21 | 0 | 334 | 8.6M | 1.0/3.3 秒 |
| 5 | 4.9 | 68 / 67 | 23 / 20 | 1 | 89 | 2.9M | 2.6/9.6 秒 |
| 10 | 9.1 | 67 / 67 | 18 / 17 | 1 | 57 | 1.9M | 2.6/12.0 秒 |
| 20 | 16.5 | 68 / 67 | 17 / 17 | 0 | 50 | 1.9M | 3.4/15.8 秒 |

**结论**

1. **批大小到 20 以内，flash 的判断准确率没有可见下降。** 每一档都和标准答案模拟器差 0 到 3 条，而且错误是零散的，不随批变大而增多。原文"批处理不伤判断"的论点，在这个规模上成立。
2. **批越大，模型越能看到前后消息的关系。** 批大小为 10 和 20 时，标准答案模拟器也会"丢"几条补充，原因是同一批里稍后的消息叫停了那张工单。flash 的判断理由是"后面的消息已经叫停这张工单，这条补充不再适用"，也就是读完整批之后做的判断。评分把它算成丢失，实际是正确行为。批处理带来的是上下文，不只是省钱。
3. **成本大幅下降。** 批大小从 1 到 20，模型调用从 334 次降到 50 次，输入 token 从 8.6M 降到 1.9M（约四分之一），单次调用时间只从 1.0 秒增加到 3.4 秒。这也说明 Router 的大部分 token 花在每次重复发送的 system prompt 和历史上，而不是卡片本身。
4. **代价全在等待时间上。** 这一组的确认延迟是人为等待造成的，不代表真实情况。真实场景下，批是 Router 忙的时候自然形成的，不应该为了凑批而让人等。合理的设计是：Router 空闲就立刻处理，忙的时候自然攒批。DSH 现在的 steer 机制就是这样做的。

**成本记录。** v4-pro 难例 3 个种子约 20 元；flash 20 条/分钟 2 个种子约 3.9 元；flash 强制批处理 8 次运行约 5.4 元。flash 每张卡片的成本约为 v4-pro 的五分之一到十分之一，这是粗算，余额扣费有延迟。

### 5.6 验证"未读消息回流"的修复

**问题回顾（§5.3）**
- 工单结束时，Worker 还没读到的人类消息会被撤回、重新送去 Eval（`Tickets.letGo`）。
- 撤回时没有任何记录，候选卡片上也不显示。
- Router 在自己的对话历史里见过这条消息，于是判定为"重复投递、已处理"并忽略，人的补充需求就此静默丢失。
- Engine 本身支持把这条消息重新挂回那张工单：已结束的工单会恢复，Worker 会重新收到它。缺的只是 Router 不知道这件事。

**修复方案（先在回放台里实现，产品代码未改）**
1. 候选卡片加 `released` 字段：列出撤回这条消息的工单。判断依据是这条消息仍在该工单的 `inputs` 里，但已不在 `fanout` 里，也不是 Worker 交回的。核心状态机不用改，从现有记录就能推出来。
2. dispatch 加一条规则：`released` 的消息不是重复投递，没有 Worker 处理过；如果仍属于那张工单就重新挂回去，否则当作普通消息处理。

**实验 `model-released`**
- 场景：10 个短工单（2 到 5 分钟），每个配 4 条不重复的补充，一半发在原 Thread、一半跨 Thread。
- Worker 从收到新消息到读取需要 60 秒。
- 每组 5 个种子。

| | 被撤回 | 到达 Router | 最终挽回 | 在 Router 处丢失 | 同 Thread 补充送达 | 跨 Thread 补充挂对 | 误建工单 |
|---|---|---|---|---|---|---|---|
| oracle | 25 | 25 | 25 | 0 | 100/100 | 100/100 | 0 |
| flash（现状） | 26 | 26 | **20** | **6** | 97/100 | 96/100 | 1 |
| flash + 修复 | 24 | 24 | **24** | **0** | 100/100 | 100/100 | 0 |

- 现状下，大约四分之一的回流消息丢失。模型给出的理由全是"已经挂过、已经投递过"。修复后一条不丢，和标准答案模拟器一致。
- 修复只是在卡片和规则上多了一点内容，token 增加约 5%。
- 第一次验证时语料里有一字不差的重复补充，两组都被拉低，但方向一致：挽回率从 18/37 升到 34/39。

**附带发现**

1. **问题严重程度取决于 Worker 多久读一次新消息。**
   - 标准答案模拟器里，读取间隔 30 秒时 3 个种子只撤回 1 次；60 秒时 19 到 40 次；120 秒时 79 次（后两个数字取决于语料版本）。
   - 原因：撤回只发生在"消息已投递、还没读"的窗口里，同时工单正好在报告完成。
   - 真实 Worker 常常卡在一个很长的工具调用里，几分钟才读一次新消息，所以线上的实际影响可能比这个实验更大。
   - 另一种修复思路：工单报告完成前，先检查有没有未读消息，有就不结束。这是在 Worker 一侧解决，可以和卡片标记一起做。
2. **评分方法修正。** 工单结束时会把已经读过的消息也从 `fanout` 里去掉，所以只看最终 `fanout` 会把"已被 Worker 确认"误判成"丢失"。评分改为看 `fanout` 或 `acked`。§5.5 的批处理数字重算后不变。
3. **语料修正。** 生成器保证同一任务内的补充文本不重复。补充条数不超过可用文本数时，生成结果和以前一致，之前的实验不受影响。

**结论**：问题真实存在，修复有效，代价很小。建议把这个修复合入产品代码。

**已合入产品代码（分支 `fix/released-inputs`）**
- `letGo` 把消息送回 Eval 时，在 Disposition 里写入 `released`；`candidateCard` 据此列出 `released`。
- `dispatch.md` 加了对应规则。
- 新增核心层、运行时、提示词三处测试。
- 用产品实现在回放台重跑：回流消息挽回 26/26，补充消息 100/100，和标准答案模拟器一致。
- Worker 一侧的"有未读消息时不报告完成"还没有做。

### 5.7 提示词修正的 A/B 验证（#4、#5）

**做法**：实验 `model-prompt` 在同一进程里，用不同版本的 dispatch 文本各跑一组 `model-hard`（flash，每组 5 个种子，130 个难例和 51 条跨 Thread 补充）。旧版本通过产品的提示词覆盖机制（`overrides['runtime/dispatch']`）注入，其余条件完全相同。

| dispatch 版本 | 难例正确 | 误建工单 | 跨 Thread 补充当成新请求 | "先别动手"被接单 | 重复请求的处理 |
|---|---|---|---|---|---|
| 原版，第 1 次 | 127/130 | 0 | 0 | 0 | 20 条全部挂到已有工单 |
| 原版，第 2 次 | 127/130 | 2 | 2 | 0 | 8 条挂，12 条忽略 |
| #4 + #5（"明确请求不管大小一律接单"） | 122/130 | 4 | 3 | 0 | 20 条忽略并回复 |
| A：只加 #5（"已有工单在做的，不开第二张，忽略并回复"） | 120/130 | 8 | 4 | 3 | 20 条忽略并回复 |
| B：#5 + 窄版 #4（"不能因为没有匹配的规则或是新功能而忽略"） | 119/130 | 7 | 3 | 4 | 20 条忽略并回复 |

原版两次运行，每个种子都在 24 到 26 分之间；三个修改版都明显更差，差距超过了运行之间的波动。

**结论**

1. **#4、#5 不改提示词。**
   - #4：在干净的运行里，"以新功能为由忽略请求"只出现了 0 到 1 次（话题相近的新需求 20/20 和 19/20）。
   - #5：原版四次干净运行里，没有一次新建重复工单。flash 对重复请求要么挂到已有工单，要么忽略，都不会造成重复工作。
   - §5.4 里观察到的两个问题都是低频现象。为它们加的规则，副作用比收益更大。
2. **提示词的改动会影响到别处。** 只是在"话题相近"那一段加一句，跨 Thread 补充被当成新请求、"先别动手"被接单的次数就都上升了，而这两类消息和新加的那句话都没有直接关系。每条新规则都会改变模型在"接单、挂单、忽略"之间的整体倾向。**改提示词前，必须在回放台上做 A/B 测试**，不能只看它是否修好了目标问题。
3. **单次运行不够，网络错误必须排除。** 第一次基线里有 18 次读取响应体时连接中断（`TypeError: terminated`），当时的重试只包住了 `fetch` 本身。被污染的那组数据看起来像"叫停常被忽略"，其实是 Router 调用失败后卡片超时造成的。现在重试已覆盖读取响应体。
4. **新发现 #10。** 没说是哪件事的"你不用管"，常被按发送人猜成叫停某张工单，原版两次运行各有 1 次。叫停是破坏性操作，这个问题值得修，修改同样要先做 A/B 测试。

**成本**：这一节共 6 组 flash 运行，每组 5 个种子，约 30 元，其中一组被网络错误污染作废。

### 5.8 叫停的指向要求（#10）

**问题**：没说是哪件事的拒绝（"你不用管""不用你弄了"），会被 Router 按发送人推断成叫停某张工单。叫停是破坏性的：进行中的工作丢掉，被人叫停的工单之后也不能再挂消息。

**固定剧本**（实验 `model-stop`，场景 `STOPS`）：困难场景的结构不变，只把不针对具体工单的难例换成两类拒绝。
- 每个种子 6 条无上下文的拒绝（`decline`）：正确做法是不叫停；
- 3 条有上下文的拒绝（`declineAfter`）：同一个人刚问完某件事的进度，45 秒后说"算了，这个我自己来改吧，你不用管了"，叫停那张工单或先问一句都算对；
- 原有的明确叫停照常保留。

新增的"叫停 对/错"统计会计入每一次叫停，包括被连锁误判带出来的叫停。标准答案在这个场景上 135/135。原困难场景的生成结果与改动前逐字节一致，此前的结果仍可直接对比。

**改法**：在 attach 规则后面加一句。
- V1："Stop only a ticket the message points at the same way; a refusal or a stop that names no work, such as “你不用管”, stops nothing: ignore it and ask which work is meant, never take the ticket from the sender's open tickets or requests."
- V2（一句话）："A stop must point at its ticket as an attach does; never infer it from who sent the message."

**结果**（flash，每组 5 个种子）

| 场景 | dispatch | 难例正确 | 叫停 对/错 | 误建工单 | 跨 Thread 补充丢失 |
|---|---|---|---|---|---|
| STOPS | 原版 | 114/135 | 21/9 | 7 | 12/41 |
| STOPS | V1 | 135/135 | 20/0 | 0 | 0/41 |
| STOPS | V1，第 2 次 | 135/135 | 20/0 | 0 | 0/41 |
| STOPS | V2 | 130/135 | 20/0 | 1 | 0/41 |
| 困难场景 | 原版（§5.7 两次） | 127/130、127/130 | — | 0、2 | — |

**观察**
1. **一次猜错会连锁放大。** 原版有 9 次错误叫停：无上下文的拒绝 7 次，有上下文的拒绝 2 次（叫停了同一个人的另一张工单）。之后：
   - 6 条明确的叫停被忽略，理由是"那张工单已经停了"；
   - 12 条跨 Thread 补充被忽略而丢失，理由都是"那张工单已被叫停"。

   9 次误停一共连带了 18 条消息。另外原版还有 4 条重复请求被接成新工单，V1 两次都是 0；这 4 条是否同样是误停引起的，没有逐条核实。
2. **V1 消除了错误叫停，也没有误伤明确的叫停。** STOPS 两次满分，困难场景两次 126 和 129，和原版两次的 127 在运行之间的波动范围内。V1 第一次在困难场景上有 2 次把"先记下，下周再做"接成工单，第二次没有再出现，原版两次也都没有。
3. **代价：有上下文的拒绝，V1 一律先问。** 15 条有上下文的拒绝全部不叫停，改为回复确认（回复数从 42 增加到 56）。这算正确，但比直接叫停多一轮往返。漏掉一次叫停只是多做一点工作，所以这个取舍可以接受。
4. **V2 更短，但有 4 张卡片到超时都没处理**，所以选 V1。
5. **没测到的路径**：回放台不发送 follow_up 通知，所以工单自己 Thread 上的"你不用管"走的是另一条路径，这次没有覆盖。那条消息会直接送到该工单的 Worker，由 Worker 自己判断是否停下（`work.md`："Decide every person's message on this ticket's own threads yourself"）。

**决定**：采用 V1，写入 `prompts/dispatch.md`，并在 `tests/cards.spec.ts` 加一条提示词契约测试。

**成本**：6 组 flash 运行，约 37 元（每组约 6 元）。

### 5.9 固定剧本与评分改进（#7）

**回放台的改动**
- **follow_up 通知**：新增选项 `followupNotices`。开启后，和产品运行时一样：人在工单自己 Thread 上发的消息送到工单的同时，Router 也会收到通知，并且可以据此叫停。默认关闭，所以此前各节的结果仍可直接对比。
- **固定剧本** `SCRIPTED`（实验 `model-script`）：12 个任务，时长 40 分钟，包含：
  - 困难场景的全部难例；
  - 2 条有上下文的拒绝（同一个人刚问完进度）；
  - 工单自己 Thread 上的 2 条叫停（`threadStop`）和 2 条拒绝（`threadDecline`），都由提需求的人发出。
  标准答案在这个剧本上 205/205。
- **评分**：
  - 同一批里工单已被人叫停时，补充没挂上记为 `moot`，不再算丢失；
  - 难例得分附上每个种子的最低和最高分；
  - 新增按代价加权的 `harm`：错误叫停 5，挂错工单 3，误建工单 2，丢失补充或漏接请求 2，其他判错 1。
- **API 过载的防护**：
  - 每次请求 120 秒超时；超时、空响应或缺少 `choices` 的响应都重试，只有最终成功那次请求的耗时计入虚拟时钟；
  - 每组统计重试次数和超过 30 秒的慢调用，出现报错、重试或慢调用的组会在结果里单独列出。
  - 起因：第一次跑这个剧本时赶上 DeepSeek 服务端过载，多次 503、空响应，单次调用长达 600 多秒。真实耗时都计入了虚拟时钟，大量卡片积压、超时，这组结果作废（约 12 元）。

**结果**（flash，每组 5 个种子，API 恢复后重跑；没有慢调用和报错，重试分别为 19 次和 49 次，等待时间不计入虚拟时钟）

**观察**
1. **V1 不影响工单 Thread 上的叫停。** §5.8 担心"没说是哪件事的拒绝不叫停"会把工单 Thread 上的拒绝也拦住。实际上，Thread 本身就指明了是哪张工单，V1 下的叫停和拒绝都 10/10 正确叫停。
2. **V1 在这个更大的剧本上同样更好。** harm 从 52 降到 16，错误叫停从 3 次降到 0 次。V1 之前最差的一个种子只得 32 分，其中 8 张误建工单。各种子的分差也从 9 分缩小到 2 分。
3. **"先记下，下周再做"是两个版本共有的薄弱点。** 改 V1 之前也有，所以不是 V1 引入的。目前出现频率不高，暂不改提示词。如果以后要改，同样先做 A/B 测试。
4. **跑模型实验前先检查 API 状态。** 服务端过载时的结果没有参考价值。现在结果里会标出受影响的组。
